# P1：记忆抽取器实验 —— 从对话到可检索条目

- 日期：2026-11-01
- 目录：`experiments/p1_extract/`
- 数据：20 段对话（4–8 轮，含闲聊噪声）+ 40 条 gold + 20 条追问
- 抽取模型：Qwen3-4B-Instruct-2507（本地，fp16，贪心解码）
- 全部〔实测〕

---

## 0. 结论

**端到端跑通了：20 段对话 → 自动抽取 → 入库 → 追问检索，top-1 = 1.000。**

| | 规则抽取 | **LLM 抽取** |
|---|---|---|
| 决策条目召回（20 条） | 0.550 | **1.000** |
| 精确（抽出的有没有用） | 1.000 | 0.909 |
| **锚词完整率** | **0.300** | **1.000** |
| **检索 top-1（L0）** | **0.550** | **1.000** |
| 检索 margin（L0） | +0.008 | **+0.142** |

**锚词完整率几乎一比一预测了检索命中率**（0.30→0.55，1.00→1.00）。
这是 P0 那条结论的闭环验证：**记忆条目缺锚词，检索就一定失败，跟模型多强无关。**

---

## 1. 任务与两种实现

### 1.1 任务定义

输入一段对话，输出结构化条目：

```json
{"entity": "星轨", "dimension": "数据库选型",
 "value": "PostgreSQL 14 单主加流复制", "kind": "decision"}
```

字段规范直接来自 P0 的实测：**实体 + 维度 + 取值，三者缺一不可**。

### 1.2 两种抽取器

| | 规则版 | LLM 版 |
|---|---|---|
| 做法 | 4 条正则匹配 value + 2 条正则抽 entity/dimension | Qwen3-4B-Instruct-2507，few-shot，prompt 里写明三条锚词硬规则 |
| 成本 | 毫秒 | 约 20 秒/段（本机 4B + CPU 调度瓶颈） |
| 输出 | 20 条（每段 1 条） | 22 条 |

### 1.3 LLM 的 prompt 要点

把 P0 的结论直接写成禁令：

> 1. entity 必须是具体名称，不能写"这个""那个"
> 2. dimension 必须说明是哪一方面
> 3. value 必须是具体取值，**绝对不能写"按之前说的""那个方案""上次定的"**
> 4. 闲聊、临时事务（会议时间、天气、午饭）一律不抽取

第 4 条起作用了：20 段对话里插了 40–60 句噪声，**没有一条被误抽**。

## 2. 主结果

### 2.1 抽取质量

| 指标 | 规则 | LLM | 说明 |
|---|---|---|---|
| 决策条目召回 | **0.550**（11/20） | **1.000**（20/20） | 9 段里规则把 entity 抽空或把项目名当成了维度 |
| 全部 gold 召回 | 0.500 | 0.500 | gold 第二条是"未采用 X 因为 Y"，两个抽取器都没抽——这是 gold 设计偏严，见 §5 |
| 精确 | 1.000 | 0.909 | LLM 多抽 2 条（D06/D17 各多一条"注意事项"），都合理但属于过度抽取 |
| **锚词完整率** | **0.300**（6/20） | **1.000**（22/22） | 核心差距 |

规则版失效的具体样子（真实输出）：

| 样本 | entity | dimension | value |
|---|---|---|---|
| D01 | 星轨 ✅ | 数据库选型 ✅ | PostgreSQL 14 单主加流复制 ✅ |
| D02 | **（空）** ❌ | **就是** ❌ | RocketMQ ✅ |
| D03 | **（空）** ❌ | **长风** ❌ | ClickHouse ✅ |

D03 把项目名"长风"当成了维度，entity 反而丢了——正则只能看到"那个({X})的"这一种句式，换个开场就崩。

### 2.2 端到端检索（三种层配置）

| 层 | 规则 top-1 | LLM top-1 | LLM margin |
|---|---|---|---|
| **L0（embedding）** | **0.550** | **1.000** | **+0.142** |
| L18（中层） | 0.050 | 0.200 | −0.000 |
| L36（最后一层） | 0.050 | 0.100 | −0.057 |

**L0 完胜，中层和最后一层基本不可用。**

这与 P0 的结论需要一处细化。P0 说"用 L0 或 L36"，但那批文本是 100–300 字的完整段落；
本实验的条目是 `"星轨 | 数据库选型 | PostgreSQL 14 单主加流复制"` 这种**短条目**，
任务本质是词面匹配 —— 而 L0 就是 token embedding 的均值，天然做词面匹配。

**修正后的选层规则**：**短条目记忆 → L0；长段落 → L36 或 L0。** 别用中层。

---

## 3. 两个值得单独说的发现

### 3.1 锚词率是检索率的下界，不是等号

规则版锚词率 0.300，检索却到 0.550。原因：有些条目虽然 entity 丢了，但 value 本身是独特技术名词（"ClickHouse""RocketMQ"），仍能在 20 条库里唯一命中。

所以更准确的表述是：**锚词完整是充分条件（1.000 → 1.000），缺锚词是高风险而非必死**。
但在真实规模（成百上千条记忆）下，靠单一 value 词命中会迅速失效——本实验库只有 20 条，偏乐观。

### 3.2 噪声过滤是免费的

40–60 句闲聊（会议改点、午饭、接电话）零误抽。这不是模型多聪明，而是 prompt 里明确写了"临时事务一律不抽"。

反过来也说明：**没有这条规则时，模型很可能会把"下午的会改到四点"也存成记忆**——这正是真实记忆系统最常见的污染源。

## 4. 对整体方案的影响

P1 补上了链路里最后一段空白。现在完整链路是：

```
对话 → LLM 抽取（实体+维度+取值）→ 条目化文本 → L0 表示 → 余弦检索
         ↑ 召回 1.000 / 锚词率 1.000        ↑ top-1 1.000
```

**成本**：抽取 20 秒/段（本机 4B，无优化）；检索一次矩阵乘。
**不需要**：任何训练。整个 P1 没有训练一步。

这意味着"对话记忆"这套东西**今天就能跑**，前提是有个能用的 instruct 模型做抽取。
唯一的工程延迟是抽取那 20 秒——异步跑、或者只在对话结束时触发一次即可。

---

## 5. 局限

1. **gold 设计偏严**：每段 2 条 gold，第二条是"未采用 X 因为 Y"。两个抽取器都没把它当独立记忆条目，所以"全部 gold 召回"只有 0.500。这个 0.5 反映的是 gold 的问题，不是抽取能力——看决策条目召回（1.000）才准。
2. **对话是模板生成的**：主题集中、没有指代回跳（"那它呢？"）、没有多人插话。真实对话的召回会明显更低。
3. **记忆库只有 20–22 条**：真实系统几百上千条，检索难度高一个量级。本实验的 1.000 是乐观值。
4. **只测了一个抽取模型**，未做 3B / 0.83B / 更大模型的对照，也没测量化后的效果。
5. **未测增量写入**：新条目进来后，已有条目的表示不需要更新（余弦检索天然支持），但去重/冲突消解（同一 entity+dimension 出现新 value）完全没做。
